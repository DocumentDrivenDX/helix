# documentor

Point it at a repository and get the documentation that repository's readers need, kept current:
pages for developers, operators, users, and data consumers, detected from what the repository is,
generated where a structured source already states the facts, written by an agent where a reader
needs explanation, evaluated by a second reader, checked in CI, and assembled into one site.

documentor implements the `guide` mode of [HELIX](https://github.com/DocumentDrivenDX/helix). HELIX
says what a guide is (the audiences, the page kinds, the writing standard, the provenance header);
documentor is the tool that detects, generates, checks, and assembles it. A repository with the
HELIX skill and no documentor still gets its guide, by hand; documentor makes the deterministic
parts exact and gives CI a gate.

## Install

```sh
uv tool install git+https://github.com/DocumentDrivenDX/helix@v0.19.0#subdirectory=tools/documentor
# or, one-off:
uvx --from git+https://github.com/DocumentDrivenDX/helix@v0.19.0#subdirectory=tools/documentor documentor --version
```

Python 3.11 or later. Hugo (and Go, for the Hextra theme) only to build a new site; a repository
with a mkdocs or Hugo site gets the pages emitted into it instead.

## Use

```sh
documentor init            # what the repository is; the publish: block for .helix.yml
documentor build           # regenerate generated pages and views, check, build the site
documentor write           # write the missing and stale pages with an agent; a second model evaluates them
documentor build --write   # all of it: generate, write, evaluate, check, build the site
documentor status          # every page and what it needs next: the agent's work list
documentor check           # the CI gate: fails when any page is missing, stale, or unreviewed
documentor review PAGE --by NAME     # record that a second reader evaluated a written page
documentor adopt PAGE --audience ID  # bring a hand-written page under the guide, unchanged
```

The written pages are written by `documentor write` (ADR-003): one agent call writes a page from its
plan entry (task, outline, budget, voice, source hints) and the checks hold it; a second call, on a
different model, evaluates it and the pass is stamped. The agent is a command, Claude Code headless
by default (`claude -p`, read tools only); `publish.agent: {command, writer, reviewer}` or
`DOCUMENTOR_AGENT` names another, and `--dry-run` prints the prompts. A page the agent wrote without
a HELIX artifact its hints name is marked `helix:gap`, and `status` shows it. `write` runs where
there are credentials; `check` needs no agent. A HELIX session (`/helix guide`) can still steer the
writing by hand. `documentor --help` and each tool's `--help` describe the rest.

## What it reads and writes

`.helix.yml` holds the decision (`documentor init` proposes it):

```yaml
publish:
  schema: 1
  traits: [databricks-app, plugin-manifests]   # what the repository is; each adds pages, generators, delegations
  audiences: [developer, operator, user]       # who reads it: developer, operator, user, data
  out: docs/guide                              # where the pages live (default: guide/ beside the HELIX root)
  traits_dir: .helix/traits                    # optional: the project's own trait files
  pages:                                       # optional: project pages, written or generated by a command
    operator:
      - id: data-jobs
        title: Example data jobs
        kind: how-to
        task: Load the example data and run the pipeline.
        sources: [data/README.md]
      - id: resources
        title: Infrastructure
        kind: reference
        generated: {command: "terraform-docs markdown table infra", sources: ["infra/*.tf"]}
  delegate:                                    # optional: pages a tool the repository has already publishes
    data/tables: {tool: tablespec guidebook, build: "tablespec guidebook specs -o guidebook", url: guidebook/index.html}
  existing:                                    # optional: hand-written pages to adopt, unchanged
    developer: ["docs/how-to/*.md"]            #   globs add pages; a mapping stands one in for an audience page
    user: {index: docs/getting-started.md}
  skip: [user/about]                           # optional: audience pages this project does not publish
  views: guide                                 # or artifact: views go between markers in the model's own documents
  site: {title: Example, repo_url: https://github.com/org/example, target: hextra}
handling:
  never_publish: [rows, sample values, or identifiers from the data]
  patterns: ['\b[0-9]{3}-[0-9]{2}-[0-9]{4}\b']
```

Generated pages come from the catalog's generators (`documentor generate --list`: app settings,
jobs, public interfaces, packages, infrastructure resources, screens, workflows, API operations,
commands, MCP tools), from a Python distribution's `documentor.generators` entry point, or from a
command the repository owns. Every generated page is regenerated and compared by `check`.

## In CI

Copy `src/documentor/catalog/ci/github-actions.yml` to `.github/workflows/guide.yml`: `check` on
every pull request, and a weekly regeneration that opens a pull request.

## Development

```sh
uv sync && uv run just test
uv run documentor check --root ../some-repo     # run the working copy against another repository
```

`uvx --from /path/to/documentor` caches the build it makes from a local path, so after a change run
it with `--refresh`, or use `uv run --project /path/to/documentor documentor ...` instead.

## Design schemas

Design artifacts declare versioned local sources in `ddx.schemas`, following
HELIX's `workflows/references/umf-schemas.md`. Hugo, static and Hextra site builds
publish a schema index, source downloads and provenance, with an embedded
`@documentdrivendx/umf-schema-browser@2.0.0`. Install that pinned package with the
site's package manager; repositories without references need no browser package.

For an existing Hugo site, run `documentor schemas --root .` before a plain Hugo
build. `documentor schemas --root . --check` rejects stale output. `documentor
site` runs schema publication automatically. The browser inspects source; native
validation and semantic compatibility remain separate checks.

### Design-stage databases and deployment

`documentor init` proposes `publish.profile: design-stage` and explicit `skip`
entries when HELIX design documents exist without application source. Review
these suggestions; remove the skips when implementation makes the pages useful.
`publish.data_mode: operational` selects an overview based on entity design and
transactions, with tables rather than analytics lineage/refresh/metric pages.
Init proposes it for upstream UMF tables without pipeline signals; set it
explicitly for other operational databases. Existing decisions remain unchanged.

The `umf-tablespec` trait detects upstream monolithic UMF TableSpec 1.0 YAML,
generates `data/tables` (columns, keys, foreign keys and an entity graph), and
publishes the same sources through `@documentdrivendx/umf-schema-browser` using
the design-schema publisher above. Install the pinned browser version in the
site's locked dependencies before building. YAML owns the schema; generated
prose does not. Descriptions and sample values are omitted; duplicate table
names fail the build.

`tablespec-pipeline` remains the tablespec integration and delegates to
`tablespec guidebook`; a `table.yaml` alone no longer identifies a pipeline.
When both traits are selected, UMF owns `data/tables` and the tablespec guidebook
is linked as `data/pipeline-tables`. An explicit project delegation still wins.

Copy `src/documentor/catalog/ci/github-pages.yml` for Pages deployment, or
`github-actions.yml` for PR checks and weekly refresh. Set Pages source to GitHub
Actions, match the upload directory to the site target, and add project-specific
locked generator/browser dependency installs before building. The template is
based on Tempo's successful [build and deploy run](https://github.com/DocumentDrivenDX/tempo/actions/runs/40952714352).
The v0.19.1 pin names the current published tool; these new capabilities require
a release containing them before a pinned consumer can use them.
