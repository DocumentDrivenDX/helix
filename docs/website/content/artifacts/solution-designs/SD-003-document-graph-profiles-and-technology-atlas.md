## 3. Proposed: profile binding (see ADR-015)

Keep `flows:`. Add optional `profile:` per entry; default `software-delivery`
so every existing marker is unchanged.

```yaml
flows:
  - id: helix
    root: docs/helix/            # profile defaults to software-delivery
  - id: atlas
    profile: technology-atlas
    root: knowledge/
```

Terminology: artifact type = `meta.yml` + template/prompt; **graph profile** =
a catalog file `workflows/profiles/<id>.yml` selecting types, allowed edge
kinds, authority model and validation tiers; **graph instance** = a flow's
documents under its `root`; **projection** = derived output (publication, UMF
export, diagram). No new engine: the skill already binds a catalog per flow;
the profile only narrows and parameterizes it.

## 4. Proposed: artifact definitions

| Type | Decision | Notes |

| Technology Assessment | New `technology-assessment` (reusable comparison, findings only, pinned briefs) | Added: a Decision Brief is contextual and cannot carry a context-free comparison several decisions reuse. |
| Decision Brief | New `decision-brief` | Contextual recommendation prior to an ADR. Feeds an ADR; never replaces it. |
| Position Paper | New `position-paper` (argued thesis, objections, limits) | Added: takes a side for an audience, unlike the assessment, and is not tied to one client, unlike the brief. |
| Publication | Extend `deliverable` (§6) | Separate type only if extension distorts the deck-script model. |

Sections are semantic expectations, not rigid mandates. `required_sections`
applies at `status: approved` or `published`, not at `draft`.

## 5. Proposed: relationships and authority (see ADR-016)

Reuse `depends_on`, `informs`, `supersedes`. Define `ddx.links` as a list of
`{id, kind, authority?, rev?}`, extending the existing `{id, kind}` shape. Initial `kind` vocabulary: `addresses`,
`evaluates`, `supported_by`, `informs`, `contradicts`. Only `contradicts` and
`authority` are new semantics.

Authority: within a flow, existing positional authority is unchanged. A
reference that crosses a flow or Atlas boundary is **advisory** unless the
consuming graph grants `governing` explicitly in its own marker or profile.

## 6. Publication and cross-graph references (pinning implemented; external resolution is runtime work) (see ADR-016)

Implemented (Phase 1): `deliverable` and `decision-brief` declare
`validation.pin_links`. At `ddx.status: approved` (or `published` for
deliverables) every `ddx.links` mapping of kind `informed_by`, `evaluates`, or
`supported_by` must carry `rev`: `git:<commit>` (content recoverable) or
`sha256:<hex>` (content verifiable only), never a branch or tag name. A link
may carry `graph:` for a source in another graph; the runtime resolves it and
`pin-sources.py` reports it without failing. `skills/helix/scripts/pin-sources.py`
provides `pin` (fill revs from git history), `check` (verify pins resolve,
report drift), and `materialize` (write each source as it was at its rev, so
any renderer builds from pinned content). Markdown stays the authoring medium;
presentation stays separate from semantics and reuses the present workflow and
its renderer. Updating a source never changes an approved deliverable; it means
a new revision of the deliverable, re-pinned and re-reviewed. Not implemented:
audience, outputs and presentation use the existing Brief, `authoring.export`
and Look fields rather than new keys, and a separate `publication` type is
introduced only if the scenario shows the extension distorts the deck-script
model. This is deliberately not an ADR yet; promote it once the scenario
confirms the shape.

## 7. Compatibility and migration

1. No `profile:` means `software-delivery`; behavior is byte-identical.
2. `flows:` stays; no `helix_version: 3` and no `graphs:` rename. "Graph" is
   documentation vocabulary.
3. `workflows/graph.yml` stays as the software-delivery graph. The generator
   grows a `--profile` option; the default output must not change.
4. New `meta.yml` fields are optional and ignored by older consumers (open
   schema). Unknown frontmatter is preserved per SKILL.md §7.
5. `ddx.links` gets a defined vocabulary; existing uses remain valid.
